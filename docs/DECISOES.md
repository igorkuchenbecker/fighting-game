# Decisões de arquitetura e projeto

| Data | Decisão | Motivo | Alternativas descartadas |
|---|---|---|---|
| 2026-08-22 | Projeto criado em `~/fighting-game/` | `~` (HOME) não estava vazio | usar `~` diretamente |
| 2026-08-22 | raylib obtido via `FetchContent` (GitHub, tag `5.5`) | stack exige raylib sem editor de engine; build reprodutível sem depender de pacote do sistema | pacote `raylib` do repositório Arch (não estava instalado); git submodule |
| 2026-08-22 | Flags de warning/sanitizer aplicadas via `CMAKE_CXX_FLAGS` nos presets, não em `target_compile_options` | `CMAKE_CXX_FLAGS` só afeta compilação C++ (nosso código); raylib é C puro, compilado com `CMAKE_C_FLAGS` — isso isola nosso `-Werror` sem quebrar o build da lib externa | flags globais via `add_compile_options` no CMakeLists (afetaria também qualquer alvo C++ de terceiros futuro) |
| 2026-08-22 | Loop de timestep fixo com acumulador (`GetFrameTime()` + `while (accumulator >= kFixedDt)`) já na F0, mesmo sem simulação real ainda | estabelece o padrão arquitetural (sim em passos discretos, render interpola/desenha último estado) exigido pelos requisitos de rollback antes que qualquer lógica de jogo exista, evitando retrabalho | `SetTargetFPS(60)` sozinho (acopla sim ao render, proibido pelos requisitos) |
| 2026-08-22 | `BUILD_EXAMPLES`/`BUILD_GAMES` do raylib forçados OFF, `BUILD_SHARED_LIBS` OFF | reduz tempo de build do FetchContent e gera lib estática (sem gerenciar `.so` no runtime) | manter defaults do raylib (build mais lento, exemplos desnecessários) |
| 2026-08-22 | Suprimir leaks de `libnvidia-glcore.so`/`libnvidia-glsi.so` via `__lsan_default_suppressions()` (só compilado quando `__SANITIZE_ADDRESS__` está definido) | driver proprietário NVIDIA aloca estado interno de contexto GL que nunca é liberado por design; ASan acusava ~6.6KB de "leak" nesse driver a cada execução, mesmo com `CloseWindow()` chamado corretamente — confirmado como falso positivo (stack trace 100% dentro de `libnvidia-*.so`, nenhum frame do nosso código ou do raylib) | `ASAN_OPTIONS=detect_leaks=0` (mascararia leaks reais também); ignorar o warning manualmente a cada rodada (não é automatizável/verificável em CI) |
| 2026-08-22 | `InputFrame`/`Direction8` (8 vias + bitmask de botões) introduzidos já na F1, não só na F2 | requisito duro de arquitetura ("input como dado puro", sim nunca lê teclado) é descrito como inegociável desde o início; só o *buffer circular* de 10 frames (item separado no roadmap) fica para a F2 | ler `IsKeyDown` direto dentro de `StepFighter` (violaria o requisito duro) |
| 2026-08-22 | `Direction8` usa `Left`/`Right` absolutos, não `Forward`/`Back` relativos a um oponente | ainda não existe P2 nem conceito de "de costas" (chega na F4); semântica relativa antes disso seria enganosa | codificar `Forward`/`Back` desde já com um "facing" fixo provisório |
| 2026-08-22 | Input amostrado 1x por iteração do loop externo (fora do `while` de steps fixos) e reaproveitado se mais de um step de simulação rodar no mesmo frame de render | requisito duro proíbe leitura de input *dentro* do step de simulação; amostrar por tick exigiria o buffer/timing que só chega na F2 | amostrar dentro do step (violaria o requisito); um `InputFrame` por tick simulado (adiado para a F2 junto do buffer) |
| 2026-08-22 | Câmera fixa implementada implicitamente (coordenadas de mundo = coordenadas de tela, sem `Camera2D` explícito) | nada ainda dá scroll/zoom; um objeto `Camera2D` parado seria só cerimônia sem efeito observável | criar `Camera2D` já agora "para o futuro" (YAGNI) |
| 2026-08-22 | Direção sempre controla velocidade horizontal, mesmo no ar (sem restrição de "controle aéreo") | mantém a F1 simples; pulo para frente/trás já funciona (segura direção ao pular) | modelar aceleração/inércia aérea separada da terrestre (prematuro antes de haver golpes aéreos na F5) |
| 2026-08-22 | `printf("tick")` da F0 removido | seu único propósito era provar que o loop de timestep fixo rodava antes de haver qualquer estado visível; a partir da F1 o retângulo se movendo já é a prova visual, e o print por tick só gera ruído no stdout | manter o print (poluiria stdout a 60/s durante o jogo) |
| 2026-08-22 | Módulos `input.h/.cpp` e `fighter.h/.cpp` extraídos já na F2, com `main.cpp` ainda pequeno (~500 linhas somadas, bem abaixo de 800) | regra do prompt manda extrair "ao passar de ~800 linhas OU na F2 (o que vier primeiro)" — F2 chegou primeiro | esperar o limite de linhas (contradiria a regra explícita) |
| 2026-08-22 | Borda de subida do botão de ataque detectada via campo `Fighter::attack_button_held` (estado interno da simulação), não lida do `InputBuffer` | `InputFrame` deve continuar sendo só dado bruto (bitmask + direção), conforme o requisito duro; "borda de subida" é estado *derivado*, pertence à simulação (`fighter.cpp`), não ao contrato de input | guardar `attack_just_pressed` como campo extra em `InputFrame` (contaminaria o contrato de input com lógica derivada) |
| 2026-08-22 | `InputBuffer` é realmente alimentado (`Push` a cada frame de render) e consultado (`StepFighter` recebe `AtDelay(0)`), não só declarado e ignorado | evita infra morta; deixa pronta a base para motion-input/replay das fases seguintes sem refatoração | criar o buffer só pra dizer que existe e continuar lendo `InputFrame` avulso |
| 2026-08-22 | FSM completa com os 14 estados do requisito duro (incl. `BlockStanding`, `Hitstun`, `Knockdown`, `Win`/`Lose` etc.) declarada já na F2; estados sem gatilho ainda viram self-loop explícito (`return fighter.state;`) até F3/F4 trazerem oponente/combate real | requisito duro pede "FSM completa" na F2; self-loop documentado não é código morto (executa toda vez que o estado está ali), só não tem porta de entrada ainda | esperar F3/F4 para declarar o enum inteiro (violaria "FSM completa" já na F2) |
| 2026-08-22 | `Fighter::facing_right` fixo em `true` por enquanto; `WalkForward`/`WalkBackward` já usam essa semântica (`Right` = forward) | sem P2 ainda não há "de costas para o quê"; a lógica de virar para encarar o oponente é da F4 | usar `Left`/`Right` cru no lugar de `WalkForward`/`WalkBackward` (não bateria com o nome dos estados exigidos) |
| 2026-08-22 | Ataque neutro não cancelável e indisponível no ar (só dispara a partir de Idle/Walk/Crouch) | moveset real (leve/médio/pesado, antiaéreo, cancelamentos) é escopo da F5; por ora só existe 1 golpe de teste para provar startup/active/recovery | permitir atacar no ar já na F2 (adiantaria escopo do "salto com ataque" da F5) |
| 2026-08-22 | Módulo `combat.h/.cpp` extraído na F3, seguindo a ordem `input, fighter, combat, stage, game` já anunciada | próximo item da ordem de extração definida no prompt | deixar hit/hurtbox dentro de `fighter.cpp` (misturaria FSM/física com resolução de combate) |
| 2026-08-22 | Segundo `Fighter` ("dummy"), parado, sem input real, adicionado só pra existir um alvo pro hit/hurtbox | "acerto gera dano/hitstun/pushback" exige um defensor; P2 jogável (teclado/gamepad) só chega na F4 — sem esse corpo de teste não dava pra validar combate nenhum | esperar a F4 pra ter um segundo lutador (impossível testar combate sem alvo); IA de verdade pro dummy (isso é F7) |
| 2026-08-22 | `kFighterStandHeight`/`kFighterCrouchHeight` promovidas de `main.cpp` pra `fighter.h` | `combat.cpp` agora também precisa (hurtbox muda de altura ao agachar); só render usava antes | duplicar as constantes em `combat.cpp` (violaria "central, sem número mágico espalhado") |
| 2026-08-22 | Bloqueio checado reativamente dentro de `ResolveCombat` (lê o input atual do defensor no instante do hit), sem um estado de "guarda" persistente | `BlockStanding`/`BlockCrouching` continuam self-loop — viram stance visual de verdade só na F4, quando segurar "pra trás" significa algo o jogo inteiro, não só no frame do hit; a mecânica de bloquear/tomar chip/blockstun já funciona sem isso | modelar a stance de guarda já na F3 (exigiria saber a posição do oponente dentro de `ComputeNextState`, que hoje só recebe o próprio `Fighter`) |
| 2026-08-22 | `ApplyHitReaction`/`ApplyBlockReaction` (fighter.cpp) chamadas por `combat.cpp` para aplicar Hitstun/Blockstun, em vez de `combat.cpp` escrever `Fighter::state` direto | mantém a regra da F2 ("único ponto de transição") mesmo com um evento vindo de fora da FSM — combat.cpp só informa o fato, fighter.cpp decide como reagir | deixar `combat.cpp` atribuir `fighter.state = ...` diretamente (quebraria a regra e espalharia a lógica de transição em 2 arquivos) |
| 2026-08-22 | Lista de estados que permitem controle direcional virou allow-list (`Idle/WalkForward/WalkBackward/Jump`) em vez da deny-list da F1/F2 | a deny-list antiga (`!= Crouch && != Attack`) deixaria `Hitstun`/`Blockstun` andando por input, o que é errado; allow-list trava automaticamente qualquer estado novo (Knockdown, Wakeup, Win, Lose) sem precisar lembrar de adicionar exceção depois | manter deny-list e adicionar `Hitstun`/`Blockstun` na exclusão manualmente (funcionaria, mas cada estado novo exigiria lembrar de excluir) |
| 2026-08-22 | Combo counter, knockdown/wakeup real, juggle e medidor de super **não** entraram na F3 | não estão no bullet de F3 do roadmap (que lista só frame data/hit-hurtbox/dano/hitstun/pushback/bloqueio/blockstun/chip); combo counter é elemento de HUD (F4), knockdown/KO fecha o sistema de round (F4), juggle/super acompanham o moveset real (F5) — são requisitos duros gerais, mas o roadmap os distribui em fases diferentes | implementar tudo do requisito duro de uma vez na F3 (inflaria a fatia muito além de "30–90 min", e sem HUD/round pra mostrar combo/KO ainda não faz sentido visual) |
| 2026-08-22 | F4 dividida em sub-fatias (F4a: P2 real; F4b: round/timer/KO; F4c: HUD), cada uma com seu próprio commit | o bullet único da F4 no roadmap (P2+gamepad, round best-of-3, timer, intro, KO, HUD) é grande demais pra uma fatia de "30–90 min"; a regra geral de fatias pequenas e verticais tem prioridade sobre o agrupamento do bullet | um commit gigante cobrindo o bullet inteiro da F4 (violaria "fatias pequenas") |
| 2026-08-22 | Gamepad lido via eixo esquerdo (com deadzone 0.4) OU d-pad, combinado com o teclado por OR (qualquer fonte pressionada vale) | "suporte a gamepad" no roadmap não especifica qual jogador; deixar os dois jogadores usarem teclado OU gamepad (P1=slot 0, P2=slot 1) cobre o requisito sem forçar hardware que o ambiente de dev pode não ter | exigir gamepad conectado (quebraria em máquina sem gamepad); só ler stick sem d-pad (menos compatível) |
| 2026-08-22 | `UpdateFacing(a, b)` chamado 1x por tick, antes dos dois `StepFighter`, define `facing_right` pela posição relativa atual | função pura de 2 posições, determinística; precisa rodar antes de `StepFighter`/`ResolveCombat` pra que `WalkForward`/`WalkBackward` e o lado do hitbox já reflitam a orientação correta no mesmo frame | recalcular facing dentro de `StepFighter` (exigiria acesso ao outro `Fighter`, quebrando a assinatura pura `(Fighter&, InputFrame)`) |
| 2026-08-22 | `BlockStanding`/`BlockCrouching` continuam self-loop mesmo com P2 real e facing dinâmico | bloqueio já funciona via checagem reativa em `ResolveCombat` (`CanBlock` aceita Idle/Walk/Crouch); um estado dedicado de "guarda" seria visualmente idêntico a `WalkBackward`/`Crouch` sem mudar nenhum comportamento — critriaria estado sem função real | criar os estados agora só pra "completar" a FSM visualmente (feature sem comportamento distinto, oposto do que as instruções pedem) |
